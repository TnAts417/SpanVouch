# SpanVouch v0.7.1 Provider-Test Isolation Design

**Status:** Approved direction
**Release target:** v0.7.1 candidate preparation
**Date:** 2026-08-10

## Goal

Make every pytest run fail closed against inherited live-provider credentials and
network access, then refresh the public engineering-validation snapshot from a clean,
reproducible v0.7.1 candidate run.

## Incident Boundary

The v0.7.0 test process inherited `DEEPSEEK_API_KEY`. Import-time API composition
therefore enabled the DeepSeek diagnoser, and
`test_deepseek_must_be_explicitly_configured` reached the configured provider path
instead of returning the expected offline `503`. This exposed a real possibility of a
paid request during an offline verification run.

The credential value must never be printed, persisted, copied into a fixture, or added
to CI. Revocation or rotation and provider-usage inspection require account authority
outside this repository and remain an explicit operator action.

## Considered Approaches

### A. Fix only the affected API test

Delete `DEEPSEEK_API_KEY` in `tests/api/test_diagnoses.py`. This fixes the observed
assertion but leaves every other test module exposed to inherited credentials and
network access. It is rejected as too narrow.

### B. Test-process isolation with a global network guard

Clear recognized provider credentials while pytest loads the root `conftest.py`, before
test modules import `spanvouch.api.app`. Install an autouse fixture that rejects DNS and
socket connection attempts. Tests may still configure fake providers or
`httpx.MockTransport` after isolation is established. This is the selected approach.

### C. Change production composition to ignore credentials under pytest

Teach runtime code to detect pytest or an `OFFLINE_TEST` flag. This would mix test
policy into production composition and create a bypassable environment mode. It is
rejected.

## Design

### Credential scrub

Create `tests/conftest.py` and remove these inherited variables at module load:

- `DEEPSEEK_API_KEY`
- `SPANVOUCH_QWEN_API_KEY`
- `OPENAI_API_KEY`
- `QWEN_API_KEY`

Module-load scrubbing is required because `spanvouch.api.app` constructs its default
application during import. An autouse fixture alone runs too late, after test modules
have already been imported.

Tests retain the normal pytest `monkeypatch` ability to set a fake credential after
collection. Provider adapter tests continue using injected clients and
`httpx.MockTransport`; no production provider adapter is replaced or weakened.

### Network guard

The same root `conftest.py` provides an autouse fixture that replaces DNS resolution
and socket connection entry points with one stable assertion failure:

`offline test attempted network access`

The guard covers `socket.getaddrinfo`, `socket.create_connection`,
`socket.socket.connect`, and `socket.socket.connect_ex`. In-process FastAPI
`TestClient`, fake providers, and `httpx.MockTransport` remain usable because they do
not open sockets.

There is no general-purpose opt-out marker. A future test that genuinely requires a
network service must live outside the offline pytest suite and receive a separate
design, authorization boundary, and CI job.

### Regression proof

Add focused tests that prove:

1. provider credentials are absent before importing the default API application;
2. the default API remains rules-only when pytest starts with hostile sentinel values;
3. DNS and socket attempts fail before I/O;
4. explicit fake-provider composition and `httpx.MockTransport` still work.

GitHub Actions runs the focused isolation test with non-secret sentinel values assigned
to all four credential names. Delivery assertions require the exact sentinel values,
forbid `${{ secrets.* }}` references, and retain the existing ban on live-provider
flags. CI never receives a usable provider credential.

### Documentation and release metadata

Prepare a v0.7.1 candidate by updating package, lock, API, citation, README, Chinese
README, release-note, and delivery-test version assertions. Add
`RELEASE_NOTES_v0.7.1.md` describing the test and CI hardening without claiming a
runtime provider change.

The v0.7.0 README and Technical Report contain a stale pre-fix Windows snapshot with
three CRLF failures. After the implementation is complete, run the full suite in a
process where all recognized provider credentials are removed, capture the actual
collected/pass/skip/fail totals and coverage, and update:

- `README.md`
- `paper/source/sections/07_results.tex`
- `paper/source/sections/08_conclusion.tex`
- `paper/IVAD.pdf`

Do not guess counts. If the final run is not green, report the observed failure rather
than describing a clean release gate.

## Failure Behavior

- An inherited provider credential is deleted before application import.
- A DNS or socket attempt raises `AssertionError` and names only the offline-policy
  violation, never the target, URL, credential, or provider response.
- A test may create a fake credential or provider after fixture setup, but it remains
  unable to reach the network.
- Production commands and deployed applications retain their existing explicit
  provider configuration and authorization behavior.

## Verification

The implementation must pass:

- hostile-environment focused regression tests;
- provider adapter tests using only mock transports;
- API diagnosis and composition tests;
- delivery and CI assertions;
- the full pytest suite with coverage at or above 91 percent;
- Ruff, mypy, wheel build, Compose validation, release verifier, PDF build and visual
  inspection, and `git diff --check`.

The full verification process must explicitly remove provider credential variables
from its own environment and must not perform provider, network, or paid calls.

## Non-Goals

- No change to production provider composition, API semantics, or authorization flags.
- No provider preflight, Qwen B4/B5 execution, formal experiment, or paid call.
- No claim change: the formal evidence remains DeepSeek-only and H1-H5 remain
  unresolved.
- No automatic credential rotation or billing inspection.
- No tag, GitHub Release, remote push, or merge without explicit publication approval.

## Acceptance

The v0.7.1 candidate is ready when a pytest process launched with hostile sentinel
provider variables stays rules-only, all socket paths are blocked, mock-provider tests
remain green, the complete offline quality gate passes, release metadata agrees on
`0.7.1`, and the public engineering snapshot matches the final captured output.
